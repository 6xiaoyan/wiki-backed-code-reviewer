日期：2026-10-19

## 1. 做完以后，用户能做什么

在 `6xiaoyan` 账号下新建一个公开仓库，放入整理后的审查项目和小型 C++/Qt 示例。用户修改示例并提交 Pull Request（PR，即请求把分支代码合入主分支），系统自动审查这次 PR 的代码改动，在 PR 中发布一条汇总报告。用户继续提交代码时，系统重新审查并更新这条报告。

第一阶段先在这个仓库内完成演示与真实使用。其他仓库一键安装、GitLab 接入和多租户服务属于后续工作。

运行方式如下：

```text
用户新建或更新 PR
    ↓
GitHub Actions 按仓库里的配置启动任务
    ↓
GitHub 提供临时 Linux 虚拟机，启动 Python 进程
    ↓
进程运行可信版本的 LangGraph 审查程序
    ↓
读取 PR 改动，按需读取周边代码与 Wiki
    ↓
生成 JSON 结果和 Markdown 报告
    ↓
独立发布任务把报告写回 PR
    ↓
任务结束，GitHub 回收临时运行环境
```

GitHub Actions 是启动和管理任务的功能；runner 是执行任务的计算机。本阶段使用 GitHub 提供的标准 Linux runner，用户无需租服务器或保持自己的电脑开机。

公开仓库使用标准 GitHub 托管 runner 的运行时间免费，但仍受平台并发、单次运行时长和使用政策限制；大型 runner 和模型 API 费用另算。不能把“免费”写成“无限制随便运行”。

## 4. 用户操作与触发规则

| 用户操作 | 系统行为 |
|---|---|
| 新建非草稿 PR | 审查当前 PR |
| 向已有非草稿 PR 推送提交 | 审查更新后的整个 PR 改动 |
| 草稿 PR 转为可审查 | 开始审查 |
| 重新打开非草稿 PR | 审查当前 PR |
| 草稿 PR 新建或更新 | 暂不调用模型，Actions 中说明跳过原因 |
| 维护者从 Actions 页面手动输入 PR 号 | 对该 PR 的当前版本重新审查 |
| PR 已关闭或合并 | 新任务不再调用模型；发布前再检查 PR 是否仍打开 |

自动事件覆盖 `opened`、`synchronize`、`reopened`、`ready_for_review`；手动入口使用 `workflow_dispatch`。第一阶段不解析 PR 评论中的命令。

同一个 PR 连续推送时，使用同一个 Actions concurrency group，并设置取消旧任务；不同 PR 使用不同组。自动运行和手动运行采用相同的 PR 分组键。这里的并发控制是让“同一个 PR 的最新审查”继续执行，不需要自建任务队列。

每次审查使用独立进程。现有 `main.py` 的进程内锁可以保留，不以移除全局状态、支持同进程多 PR 作为本阶段前置条件。不同运行的输出目录、缓存与可写规则目录不能共享。

## 5. 可信程序与 PR 代码如何分开

公开仓库允许陌生人从 fork 提交 PR。程序需要模型凭据，因此必须明确哪些文件可以执行。

本阶段默认采用 `pull_request_target` 触发可信工作流；审查程序、安装依赖清单、Wiki、skill、提示词、预算配置都来自本次记录的可信目标分支提交。手动运行只接受默认分支上的工作流；读取指定 PR 后，同样使用可信目标分支的审查程序。

PR 分支里的文件只作为数据读取：不能把 PR head 检出到可执行工作目录，不能导入其中的 Python 模块，不能运行其中的安装、构建、测试、Git hook 或任意脚本。推荐通过只读 Git 对象或固定 SHA 的 GitHub API 获取文件；如使用 Git 获取对象，不创建 PR head 的可执行工作树。

尤其要检查现有 Agent 工具：在 PR 模式中只允许读取指定快照、搜索代码、查询可信 Wiki、提交结构化问题。禁用任意 shell、任意外网访问、写规则、写 skill 和直接调用 GitHub 发布接口的能力。代码注释、PR 描述和模型输出不能改变这些工具权限。

工作流分成两个 job（job 是一次工作流中的独立任务，标准托管环境中各自运行）：

| job | 凭据与权限 | 职责 |
|---|---|---|
| analyze | `contents: read`、`pull-requests: read`；模型 API Secret | 获取快照、生成 diff、运行审查、导出结构化结果 |
| publish | `contents: read`、`pull-requests: write`；无模型 API Secret | 校验结果、检查最新 head、更新汇总评论 |

默认工作流权限设为只读，写权限只授予 publish。发布程序和校验代码来自可信提交，不能执行分析产物中的任何代码。工作流引用的第三方 Actions 固定到已核实的提交 SHA。

若执行 agent 无法证明以上边界，应先实现只接收维护者手动触发的可信审查，并把自动 fork 支持列为未完成项，不能用“带 Secret 检出并运行 PR 分支”替代。完整验收仍要求满足本节的自动触发边界。

## 6. 具体审查哪些代码

diff 是两个代码版本之间的改动。本阶段审查“当前 PR 从分支共同起点到最新提交的全部变化”，每次 push 都重新审查这个范围。它不等于整个仓库，也不等于只检查最后一次 commit。

启动时记录以下 Git 提交标识；SHA 是 Git 用来标识提交版本的字符串：

- `base_sha`：读取 PR 时，目标分支的版本。
- `head_sha`：读取 PR 时，PR 分支最新版本。
- `merge_base_sha`：两个分支的共同祖先。

用 `merge_base_sha → head_sha` 生成 diff。运行期间读取的代码都必须属于这些固定版本，不能反复使用可变化的分支名。找不到共同祖先、API 数据被截断或读取文件失败时，明确报错，不能把失败当成没有改动。

### 6.1 变更文件与周边代码

1. 从 diff 建立新增、修改、删除、改名文件清单，记录旧路径、新路径与前后行号。
2. 确定性检查可以读取整个变更文件，但发布的问题必须与本次改动有关。
3. 模型优先读取变更片段、所在函数或类、直接相关的头文件/实现文件。
4. 只有理解问题确实需要时，再读取关联调用点或其他文件；每次读取记录路径、范围和用途。
5. 二进制文件、生成文件、第三方目录和不支持的文件类型记录为排除项，不发送给模型。

不能为了准备输入先递归读取所有源文件全文，再在报告阶段过滤为改动文件。可以获取 Git 元数据与文件路径索引，但模型审查输入和文件内容读取必须受范围与预算约束。

C++、Qt、SQLite 检查按文件与内容适用性运行；Git 规范检查只看共同祖先之后、属于 PR 的提交范围，不能沿用“最近若干条全仓提交”的默认逻辑。

### 6.2 如何避免把历史问题当成 PR 新问题

- 新增行里明确引入的问题，可以作为本次发现。
- 修改行里原本存在的问题，需要比较修改前后；纯粹搬动、改名或保留的历史问题不能直接算新引入。
- 删除校验或保护逻辑导致的问题，可以定位在删除行或关联代码处，但必须引用删除前后证据，说明因果关系。
- 证据不足的候选保留在完整结果的 `uncertain_findings` 中供人工查看，不进入“已确认问题”数量，不作为合并阻断依据。

第一版不承诺完整的跨文件数据流分析。报告应说明实际审查范围与未覆盖部分。

没有适用改动时，结果为 `skipped`，说明原因；不能显示“所有代码安全”。仅修改审查程序、Wiki、skill 或工作流时，这些修改不改变本次审查标准；报告说明它们是审查配置候选，本阶段不执行 Wiki 评测或发布。

## 7. LangGraph 如何接入

新增 PR 专用入口，接收标准输入对象，避免让领域 Agent 直接依赖 Actions 环境变量。建议入口名称为 `python -m code_checker.pr_review`，名称可以按项目组织调整。

```text
读取 PR 与固定版本
    → 生成 diff 和审查文件清单
    → 确定性检查
    → 适用的 C++ / Qt / Git / SQLite Agent
    → 核验代码证据、规则依据与改动关联性
    → 合并去重
    → 导出 JSON 和 Markdown
```

优先复用现有检查逻辑，但 PR 入口不能调用全仓 scanner 后再过滤报告。现有修复节点、Wiki 仲裁、skill 自动积累与旧缓存写入在 PR 模式中关闭，可信规则目录保持只读。需要的临时文件写到本次运行独有目录。

现有降级机制允许模型失败后返回空列表，PR 模式必须捕获并记录这种情况。某个必要 Agent 没运行完时，不能生成“未发现问题”的完整结论。

## 8. 每轮保存什么，如何防止旧结果覆盖新结果

每次运行写入 `ReviewRequest`，至少包括：仓库、PR 号、上述三个代码 SHA、审查程序提交 SHA、规则/skill 摘要、提示词与非敏感配置摘要、模型提供方与模型标识、Actions run ID、attempt 和预算。

三个容易混淆的版本，按以下方式处理：

| 版本 | 举例 | 本阶段的实现 |
|---|---|---|
| 被审查代码版本 | PR 分支这次提交 | 保存 `head_sha` |
| Wiki 与 skill 版本 | 本次用到的命名规则、SQLite 规则和已有检查经验 | 使用可信提交中的内容，保存该提交及内容摘要；候选 PR 不改自身标准 |
| 审查程序、模型与提示词配置 | 哪版 Python 程序、调用哪个模型、使用哪些提示词 | 保存审查程序提交 SHA、模型标识、非敏感参数及提示词摘要 |

这些信息用于解释和追查一次结果，不保证外部模型再次调用时逐字复现。API Key 不进入任何版本摘要、报告或交付物。

用仓库、PR、代码 SHA 和审查配置计算 `review_key`，标识相同的一组输入；Actions run ID 与 attempt 标识实际执行。第一阶段只要求记录这些值和重复执行安全，不要求持久缓存或跨任务复用计算结果。

发布前重新读取 PR：如果最新 head 与本次 `head_sha` 不同，或 PR 已关闭，则结果标为 `superseded`，不更新 PR 汇总评论。取消旧任务是节约资源；发布前检查是防止旧结果覆盖新结果，两步都要做。

GitHub 评论更新不支持按 head 做原子条件写入，因此报告始终明确写出被审查 SHA，不能只写“最新代码已通过”。在实际写评论前尽量再次检查 head；若发布期间发生新提交，下一轮会更新报告，旧 SHA 报告不能被描述为新提交的审查结论。

## 9. PR 中显示什么

每个 PR 只维护一条由机器人创建的汇总评论，用隐藏标记识别，例如 `<!-- wiki-backed-code-reviewer:summary:v1 -->`。查找时同时核对评论作者与标记，不能修改用户伪造标记的评论。重跑更新同一条评论，不连续刷屏。

报告至少包含：

- 本次审查的 head SHA、审查时间、运行链接和结果状态。
- 已审查文件数、变更行数、排除文件与未完成范围。
- 已确认问题的严重度、文件与行号、代码证据、规则 ID/页面来源、说明和修复建议。
- 不确定候选的数量与完整报告入口，避免混入已确认发现。
- 模型或工具失败、预算中止与数据读取错误。
- 完整报告和 JSON 的 Actions artifact 链接；artifact 是可下载的本次运行文件。

示例：

```text
PR 审查完成：发现 2 个问题
代码版本：abc1234
已审查：3 个 C++ 文件、42 行改动；排除：1 个图片文件

1. warning — examples/review-target/db.cpp:28
   问题：……
   本次改动证据：……
   依据：sqlite/参数化查询
   建议：……（建议未执行验证）

规则版本：……；审查程序版本：……；模型：……
完整报告 / 运行记录：……
```

页面评论控制在可发布长度内，优先显示严重问题；超出部分保存在完整报告中，明确说明省略数量。对模型生成的文本校验长度与结构，转义或移除自动 @ 提醒等副作用内容，不拼接到 shell 命令中。

第一阶段不要求额外创建关联 PR head 的自定义 Check Run。Actions 自带的运行状态和 PR 汇总评论分别表示任务执行情况与审查结论，文档不能声称已配置“合并前必须通过的审查门禁”。

### 9.1 状态必须区分

| JSON 状态 | 含义 | 展示与任务结果 |
|---|---|---|
| `completed` | 所有必要阶段完成，可能有问题，也可能没有 | 显示已确认问题数量；有问题本身不使工作流失败 |
| `skipped` | 草稿或没有适用改动等 | 说明原因，不宣称检查通过 |
| `incomplete` | 预算耗尽、部分读取失败、必要 Agent 未完成 | 明确“审查未完成”，保留已有发现；发布后分析任务以非零状态结束 |
| `failed` | 缺少配置、鉴权失败、无法准备 diff 等 | 明确失败原因；任务失败 |
| `superseded` | 已有新提交或 PR 已关闭 | 不更新 PR 评论，记录原因 |

Actions 原生的排队、运行和取消状态用于展示执行进度，不需要复制为自建任务系统。被平台直接取消的任务可能来不及导出 JSON，不能承诺所有取消任务都有 artifact。

analyze 即使发生可捕获错误，也尽量导出失败结果；publish 在存在合法结果时执行，包括分析失败的情况。校验结果 schema、大小、仓库、PR、head 和来源 run 一致性后才发布。分析进程崩溃导致没有合法产物时，Actions 显示失败，不能用上一次成功报告冒充本次结果。

## 10. 预算、费用与运行记录

所有限制来自可信配置，PR 作者不能通过修改 PR 内的配置提高额度。建议初始默认值如下；执行 agent 可按实际试跑调整，但必须记录最终数值与原因：

| 限制 | 初始默认值 |
|---|---|
| 单 PR 适用变更文件 | 50 个 |
| 适用文件的新增与删除行合计 | 3,000 行 |
| 单个可读取文本文件 | 256 KiB |
| 额外上下文累计读取量 | 2 MiB，按路径、版本、范围去重计量 |
| 单轮模型请求总数 | 40 次，所有 Agent 与重试共同计数 |
| 审查阶段时限 | 15 分钟 |
| Actions 工作流总时限 | 20 分钟 |
| 模型瞬时错误重试 | 每次调用最多重试 2 次，计入总预算 |
| 运行交付物保留时间 | 14 天 |

超过范围上限时，明确标为 `incomplete` 并要求拆分 PR 或由维护者调整可信预算，不静默只审查前若干文件。模型调用包装层统一计数与限制，不能每个并行 Agent 各拿完整 40 次额度。发布任务不调用模型。

记录每阶段耗时、上下文读取量、模型请求次数、返回的 token 使用量、失败与重试次数。接口未返回 token 数时标为未知；没有可信价格配置时不虚构美元金额。运行记录默认不保存完整模型对话，不公开凭据或不必要的源代码副本。

模型凭据通过 GitHub Secrets 配置。运行时没有凭据要清楚报错；可以有单独离线测试模式，但不能把离线规则检查标为完整 LLM 审查。

## 13. 验收条件

开发工作需要自动化测试与 GitHub 实际运行证据。解析、范围、状态与权限用确定性测试验证；模型语义结果允许波动，演示使用已有稳定确定性规则，不能用假模型输出冒充线上审查。

| 场景 | 必须观察到的结果 |
|---|---|
| 仓库公开发布 | `6xiaoyan` 下可访问；只含整理后的项目，无真实凭据、个人材料与旧 trace |
| 干净 Linux 环境 | 按 README 能安装；不依赖开发者电脑绝对路径或本地 MCP 服务 |
| PR 新建 | 自动触发；在 PR 产生一条汇总评论与真实运行链接 |
| 修改一个小 C++ 文件 | 输入记录只含改动文件及已说明用途的关联内容，没有先读取全仓源码全文 |
| PR 引入稳定规则违规 | 报告包含真实位置、代码证据、规则依据，已确认问题至少有一条 |
| 同文件中保留无关历史违规 | 不把历史违规记为此次新增；完整结果可解释过滤原因 |
| 新增、删除、改名及多次提交 | diff 与定位正确；第二次 push 仍覆盖整个当前 PR 的改动 |
| 连续推送 A、B 两版 | A 被取消或发布前判为过时；PR 结果明确对应 B；测试覆盖发布前 head 改变 |
| 重跑同一 PR | 更新已有机器人汇总评论，不重复刷屏、不修改用户评论 |
| 无适用文件或草稿 | 显示跳过原因，不调用模型，不显示完整审查通过 |
| API 超时、429、缺凭据或阶段失败 | 按策略重试；最终显示未完成或失败，不显示零问题完整通过 |
| 超预算或差异数据不完整 | 明确未完成范围；不静默丢弃文件 |
| fork PR 改动审查脚本、依赖或工作流 | 当前运行仍使用可信程序和规则；PR 代码不被执行，Secrets 不进入 PR 文件或日志 |
| fork PR 加入诱导执行命令的注释 | 不能获得 shell、写规则或 GitHub 发布权限；工具约束测试证明调用被拒绝 |
| PR 已关闭或在发布前出现新 head | 不发布旧结论；原始结果与 Actions 状态可追查 |
| 规则/skill/提示词修改 | 本轮使用原可信版本，结果保存实际使用版本；不自动写入或发布候选 |
| 模型和发布任务隔离 | analyze 没有 PR 写权限；publish 没有模型凭据并校验产物 |
| 本地旧入口 | 至少完成现有离线模式的兼容性检查，说明受影响行为 |

如果缺少用户才能配置的模型凭据或 GitHub 权限，执行 agent 应完成不依赖该凭据的实现与测试，列出未完成的在线验收项与准确缺口。不得创建假的成功截图、报告或运行链接。
