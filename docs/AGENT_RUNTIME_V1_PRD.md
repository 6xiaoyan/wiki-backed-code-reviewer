# PR 审查 Agent Runtime V1 PRD

日期：2026-10-23  
状态：供开发 Agent 实施；本文是需求与验收定义，不代表功能已经完成。  
实施项目：`D:\ai_share\langgraph\wiki-backed-code-reviewer`。该目录为独立发布仓库；不要以原工作区的旧实现覆盖发布仓库。  
部署假设：约 20 人团队，一台固定虚拟机执行审查，SQLite 文件位于该机器的持久本地磁盘。

## 1. 本阶段要完成什么

让 PR 审查通过 SQLite 持久化排队，最多同时执行两个任务；每个任务最多同时发起五个模型请求，并在模型故障、进程退出、人工取消、PR 更新时有明确且可恢复的行为。

核心验收场景：一个 PR 有 10 个待审文件，其中 4 个结果已保存，其他文件执行中或尚未开始时进程被终止。启动新进程恢复同一任务后，复用这 4 个结果，只继续尚未完成的工作；请求预算不重置，报告不重复收录问题，发布不重复创建评论。如果 PR 已有新提交，旧任务不能继续调用模型或发布旧结果。并发完成顺序不保证与文件列表顺序相同。

Runtime 指负责执行管理的程序层：安排执行单元、检查预算、分类失败、决定重试、保存进度和响应取消。代码审查规则、diff 解析、证据判断仍由现有审查逻辑负责。

第一版采用一个管理进程和两个执行进程；执行进程称为 worker，各自一次处理一个审查任务。管理进程调度 SQLite 中的待执行任务，服务级任务并发上限为 2。每个任务内部的独立文件可异步并发审查，所有领域、文件和重试共享 5 个模型请求并发名额。取消、提交和查询命令可在其他进程运行，不占用执行槽。

## 3. 部署方式与数据库选择

SQLite 保存任务和进度，不会自行执行任务。管理进程负责领取和安排工作，worker 负责运行 runtime。服务启动后扫描待执行任务；确认原执行进程退出后，将可恢复的中断任务重新排队。保留人工恢复入口；操作系统级自动重启服务可后续接入。

数据库路径必须可配置，位于工作区之外的持久目录，例如 `/var/lib/wiki-backed-code-reviewer/runtime.sqlite3`。不得把数据库提交到 Git、放入 PR 工作树或直接放在共享网络文件系统上。

启用外键、WAL 模式和有限的写锁等待；建议写锁等待上限 5 秒。事务保持短小，调用模型、GitHub 或读取大文件期间不持有写事务。采用适合崩溃恢复的同步配置，并在运维文档说明选择。使用 SQLite 备份 API 或等效一致性备份方法；不能只复制运行中的主文件而忽略 WAL。

当前 Actions 的 `ubuntu-24.04` 是临时执行机器，不具备本 PRD 所需的共享本地持久磁盘。保留其现有运行方式，不能声称已经支持跨 Actions 运行恢复。恢复验收在固定虚拟机或本地持久目录上完成。

若后续把虚拟机配置为 self-hosted runner（接收 Actions 任务的团队机器），再单独配置访问权限和可信工作流；本阶段不自动改为 self-hosted、不执行 PR head 代码。已有 analyze/publish 权限与凭据分离继续生效。

### 3.1 SQLite 队列与接收入口

任务必须在 SQLite 提交成功后才返回“已受理”和 `run_id`。接收入口只做必要校验和持久化，不等待整次审查完成；查询结果或 PR 评论用于获取最终报告。本阶段提供 CLI 提交与服务进程，不要求新增 Web 服务或 GitHub webhook 服务。

队列可以直接由 `runs` 表的状态及调度字段实现，无需单独部署消息中间件。按提交顺序领取符合执行条件的任务；领取必须在短事务内完成待执行状态检查、状态修改、执行者绑定及事件记录，不能让两个 worker 领取同一任务。

同一仓库同一 PR 只允许一个任务实际执行。新 head 入队时，旧的待执行任务直接标记 `superseded`，旧的执行中任务收到取代请求；确认旧执行者结束后，新任务才能执行，避免同 PR 发布和预算状态交叉。

队列必须有容量和等待时间限制，默认待执行任务上限 100、最长排队时间 3600 秒，均由可信配置调整。这是第一版保护性默认值，不是吞吐能力承诺。容量已满时明确拒绝新任务，不返回受理成功；重复请求去重和旧任务取代后再判断容量。超过排队时限的任务不执行模型调用，记录失败原因 `queue_timeout`。

### 3.2 两层并发与异步等待

| 配置 | 默认值 | 范围 |
|---|---|---|
| `max_running_runs` | 2 | 整个服务正在占用执行槽的审查任务数 |
| `max_model_concurrency_per_run` | 5 | 一个任务内所有领域、文件及重试共享的模型请求并发数 |
| `max_model_requests` | 沿用现有默认值 40 | 一个任务累计请求尝试预算，完成请求不返还预算 |

每个任务构造一个共享的异步并发限制器，例如 `asyncio.Semaphore(5)`。不能每个领域各建五个名额，也不能每次调用重新创建限制器。所有模型调用通过同一个受控入口；只有两个 worker 且不存在旁路调用时，正常运行的客户端在途模型请求总量不超过 10。

异步并发限制器只对所属进程和事件循环有效，不能拿它当跨进程全局锁。服务级上限通过管理进程和两个执行槽保证。模型服务端可能继续处理已超时或进程崩溃前发出的请求，因此不承诺供应商实际执行中请求永远严格不超过 10。

等待名额和网络响应必须让出事件循环。等待名额期间不持有 SQLite 事务，不预占累计调用预算；拿到名额后再次检查取消、截止时间和预算，再持久化预占并发起请求。实际调用结束后释放名额；重试退避不占用模型请求名额。

优先使用支持异步网络等待的模型客户端。同步网络调用、Git 子进程等待和可能长时间阻塞的数据库操作，不得直接阻塞事件循环；按需采用异步 API 或受控线程池。短小的同步代码无需机械改为异步。同步线程调用被取消或上层超时后，不得把仍在运行的底层调用当作已结束并释放本地名额，导致实际并发超限。

独立文件可并发执行，有输入依赖的上下文构造、模型调用、核验仍按依赖顺序执行。不能简单把整个现有领域循环并发化而共享不安全的可变状态。预算更新、发现保存、规则引用范围和任务状态必须按任务隔离，最终报告按稳定规则排序。

并发数不等于每分钟请求数或 token 数；第一版不实现自动推算供应商额度，仍使用统一 429 退避策略。配置说明必须提醒部署方按模型账户额度调整并发，不能把“最多 10 个在途请求”写成“不会限流”。

`snapshot.read_text()`、上下文构造等高层函数内部可能访问 Git 或 GitHub；不能因为函数名像本地读取就忽略底层等待。新增 SQLite 写锁等待、checkpoint saver、文件读写和 trace 输出也必须检查是否进入事件循环线程。

处理原则：

- 普通字段检查、短字符串处理等快速同步代码可保留；关注一次连续执行以及批量循环的累计占用时间，不要求给每行代码加 `await`。
- 异步等待共享一个事件循环，长期同步调用会阻止同进程其他协程、取消检查和定时器推进；这不等同于 GIL 问题，也不意味着每次阻塞都会崩溃。不能依赖同一事件循环的超时回调打断正在执行的同步阻塞函数。
- 线程池作为同步 I/O 适配层，必须显式限制线程数与待执行工作量；不能每次请求新建线程或无界提交工作。已使用原生异步接口的操作无需再套线程池。
- 线程池中的同步等待仍然占用工作线程；协程被取消不代表底层线程停止。保留底层完成状态，遵循第 3.2、9 节的名额与执行槽释放要求，防止遗留线程继续访问新任务状态。
- 数据库连接按驱动要求由所属线程使用，或使用专用数据库执行通道；不能将同一 SQLite 连接直接跨线程并发使用，也不能仅关闭线程检查就认为线程安全已经解决。保持短事务和按任务隔离。
- 若定位到持续占用 CPU 的代码解析或核验，单独测量和处理；线程池不保证加速 Python 密集计算，不得将所有性能问题都归为网络阻塞。

必须测量事件循环延迟：用固定周期心跳比较计划唤醒和实际唤醒时间，同时记录被测操作耗时，以定位长时间没有交出执行机会的路径。CPU 使用率低、协程数量多，或只在源码出现 `async/await`，都不能作为“没有阻塞”的证据。

离线验收使用 100 毫秒心跳和至少持续 2 秒的可控假网络/假同步 I/O。在低负载测试环境中，正向实现的心跳最大间隔应不超过 500 毫秒；若环境调度抖动导致失败，记录环境并复测，不能无依据放宽到秒级。增加会直接同步阻塞的负向对照，确认检测确实能发现问题。该阈值用于受控验收，不是所有生产负载下的延迟承诺。

开发 Agent 必须在交付说明逐项报告：原位置、采用的异步接口或线程池适配、线程/请求上限、取消与超时行为、验证结果及未处理路径。不能只写“已支持异步”，不能以把整个审查放进一个后台线程替代文件级并发和取消验收。

## 4. 任务身份与固定输入

必须区分以下标识：

| 标识 | 含义 |
|---|---|
| `run_id` | 一次逻辑审查任务，恢复时沿用 |
| `execution_id` | 一次进程执行，恢复启动后重新生成 |
| `unit_id` | 任务内一个可独立恢复的执行单元 |
| `attempt_id` | 执行单元的一次实际尝试，每次重试重新生成 |

任务保存仓库、PR 编号、base SHA、merge-base SHA、head SHA，以及可信审查程序、Wiki、skill、提示词、模型和预算配置的版本或内容摘要。Secret 只在执行时读取，不进入摘要原文、数据库、事件或 trace。

恢复必须使用原任务固定输入，不能悄悄切换最新 Wiki、模型、提示词或代码版本。不兼容的程序版本或状态 schema 必须明确拒绝恢复；如果需要新配置，创建新任务。拿不到固定 Git 对象或规则内容时明确报错，不改用当前工作树凑合执行。

同一任务重试、恢复沿用 `run_id`。用户要求“重新审一遍”则建立新任务和新预算，不能冒充恢复。第一版不需要自动合并所有重复触发，但重复投递同一个明确的启动请求编号时，应返回已有任务。

## 5. 执行单元与 checkpoint

Checkpoint 是可用于继续执行的持久状态，包含已完成工作、结果引用和执行位置；不等于普通日志。

建议执行顺序：

```text
固定输入、解析 diff、保存审查范围
  → 确定性检查
  → 逐文件模型审查与证据核验
  → 汇总与导出
  → 独立发布
```

模型审查必须按文件拆成独立执行单元；一个领域有多个文件时，不能只在整个领域循环结束后才保存进度。一次文件单元可包含上下文构造、模型调用和核验，但必须允许复用已保存的有效模型响应，避免核验阶段崩溃后再次调用模型。

每个单元保存输入摘要、状态、尝试次数、已完成输出及必要的模型有效响应。有效响应必须先通过格式和大小检查；输出按现有报告 schema 限制，不保存无限长原始响应。

保存成功单元的结果、状态和对应运行事件时，使用数据库事务。重试保存以 `(run_id, unit_id)` 唯一定位同一份结果，不能重复追加。最终报告从唯一结果集合重建，不能从“已发出的事件数量”推断发现数量。

复用 LangGraph 的持久化能力，但不能假设任意循环、局部变量或 Python 对象会自动恢复。LLM 客户端、Git snapshot、数据库连接、锁、内存预算对象由恢复进程根据可信配置重新构造。

文件结果与预算台账是业务恢复的依据；LangGraph checkpoint 管理图执行位置。若两者无法在一个事务保存，必须实现一致性校验：图节点重放时先查找相同输入摘要的已完成单元并复用结果。不能因为图 checkpoint 稍旧就再次调用已完成文件的模型，也不能因为游标靠前就跳过尚未保存的结果。

## 6. 执行预算

沿用当前可信预算默认值，包括模型请求次数、单文件大小、文件数、改动行数、规则正文和额外上下文限制。重构时不得静默改掉默认值。

| 预算 | 要求 |
|---|---|
| 模型请求次数 | 每次实际尝试调用前持久预占；重试、超时、崩溃中的调用均消耗额度 |
| 尝试次数 | 按单元/调用保存，恢复不清零 |
| token | 响应提供用量时记实际值；无法确定的请求记录 `usage_unknown`，不得记成零费用 |
| 排队时间 | 从首次提交时间计算最长排队时限，独立于实际审查时间 |
| 执行时间 | 第一次领取执行时生成并保存任务绝对截止时间；恢复、重试和名额等待不延长截止时间 |
| 额外上下文 | 保存计量记录，同一固定版本、路径和范围复用时不重复计入读取预算 |
| 规则与代码范围 | 沿用已有限制及未覆盖记录，恢复不扩大范围 |

模型请求额度预占和尝试记录创建必须在同一短事务完成。预占后进程可能在真正发送前退出，第一版允许保守地消耗一次额度，不返还不确定请求的额度。

并发请求必须通过原子预占共同消耗同一任务预算，不能先在各协程读剩余次数、再各自无条件递增而超发。请求并发名额与累计预算分别计量：调用结束归还并发名额，不归还累计次数。恢复进程重建并发限制器，同时保留数据库中的累计消耗。

初次排队不消耗执行时间预算；任务第一次开始后，执行截止时间包含故障停机和恢复排队时间，不能通过重新排队刷新。超过截止时间的中断任务直接生成未完成结果，不再调用模型。

token 第一版作为用量统计；不能承诺严格人民币/美元费用上限。供应商未返回用量时，在报告显示未知用量次数。

预算不足时不再发起调用，保留已完成结果，输出 `incomplete` 及未覆盖范围。恢复预算耗尽的任务不能获得新额度；用户要增加额度应创建新任务。

## 7. 异常分类与节点重试

捕获异常不代表全部重试。统一输出错误类别、是否可重试、脱敏原因和下一次执行时间。

| 类别 | 示例 | 行为 |
|---|---|---|
| 临时外部故障 | 429、连接错误、可恢复的 5xx | 有限重试，指数退避加随机扰动，受预算与截止时间约束 |
| 响应格式无效 | 空响应、畸形 JSON、结构不符合约定 | 有限重试；耗尽后文件未完成，任务 `incomplete` |
| 配置或权限错误 | 无效 Key、模型不存在、403 | 不自动重试，明确指出所需修正 |
| 输入或程序错误 | diff 解析失败、确定性代码异常 | 不盲目重试，保存阶段和错误 |
| 本地短暂写锁冲突 | `SQLITE_BUSY` | 有限等待；不得触发再次调用模型 |
| 控制条件 | 预算耗尽、截止时间到、取消、被新任务取代 | 停止后续执行，不进入普通重试 |

复用现有模型重试次数配置；第一版退避建议起始 1 秒、上限 30 秒。服务商提供 `Retry-After` 时遵守，但不能越过总截止时间。下一次尝试时间需要保存，恢复不能绕过限流等待。

重试只由一个明确层负责。检查并配置模型 SDK 的内部重试，避免 SDK、文件节点和整个工作流层层叠加。重放图节点不等于获得新的重试次数。

业务运行边界记录未处理异常后结束，不吞掉错误伪装成“无发现”。沿用已有失败/部分完成判定，写出已完成和未完成的范围。

## 8. 恢复、重复执行与执行所有权

恢复前依次检查数据库 schema、固定输入版本、截止时间、预算、取消状态、PR 当前 head 和执行所有权。确认原单元完成且输入摘要一致后，复用保存的结果。

如果上次尝试处于执行中、但进程已经退出，将该次尝试标为 `interrupted` 或 `outcome_unknown`。外部请求是否完成无法判断时明确记录；允许预算内再次尝试，但不承诺供应商不重复生成或计费。

同一 SQLite 实例第一版只允许一个管理进程和最多两个占用执行槽的 worker。使用同机管理进程锁及执行槽锁或等效机制；第二个管理进程报忙，不能另起两个 worker 绕过总上限。同一 `run_id` 不能由两个进程执行。

进程标识须能区分 PID 被操作系统复用的情况。确认原进程退出后才能回收其任务；不要仅凭心跳过期抢占仍可能活着的执行者。管理进程重启时，必须识别仍存活的子进程并继续计入执行槽，或先确认其终止后再启动替代者。数据库中标为运行不等于进程一定存在，反过来也不能因管理进程退出就假设子进程已经退出。

查询、提交、取消命令不持有 worker 执行槽锁，允许在另一进程运行。心跳供人工判断进程情况，不作为 PR 审查结果。外部模型调用的超时和未知结果仍遵循第 6、9 节的保守计量规则。

幂等性要求：

- 结果保存：相同单元重复提交结果时只保留一份可用结果；发现汇总不重复计数。
- checkpoint 重放：保存成功的文件不再次请求模型。
- GitHub 发布：沿用机器人作者与隐藏标记查找，优先更新已有评论；网络超时后先核对远端状态，再决定创建。
- 同仓库同 PR 的发布必须串行并在写前核对当前 head；不同 PR 可各自发布。部署方不得同时启用另一套无协调的发布入口，并在文档中明确这个前提。
- 不宣传跨数据库和 GitHub 的“恰好一次”事务。创建评论结果不确定且无法重新查询时，保留未知状态，不能盲目再次创建。

## 9. 取消与新任务取代旧任务

取消分为人工 `cancelled` 和 PR 更新导致的 `superseded`，记录原因和请求时间。取消请求写入 SQLite，worker 在启动单元前、调用模型前、重试等待中、保存返回结果后和发布前检查。

待执行任务可直接取消且不得调用模型。任务内等待模型并发名额的协程也必须响应取消与截止时间，不能拿到名额后继续发送已取消请求。执行中任务停止启动新文件，妥善处理所有在途调用；仅当本地执行者和相关操作结束或完成受控隔离后释放服务级执行槽，不能把状态改成取消就立刻复用仍被占用的槽。

等待退避时至少每秒检查一次取消。正在执行的外部调用使用有限超时；同步调用不能中止时等待返回或超时，但收到取消后不能启动下一次调用或发布旧报告。服务商仍可能处理并计费，报告不能声称已撤回请求。

接收到 SIGTERM 等可处理信号时，尽量记录取消并结束；SIGKILL 无法执行清理，依靠已有持久状态恢复。接收 SIGTERM 不保证最终 artifact 一定生成。

PR head 改变时旧任务成为 `superseded`，不复用旧结果审查新 head。恢复前和发布前重新读取 PR head；每次外部模型调用前检查持久取消标记，并在文件边界刷新 PR head。明确存在轮询检测延迟，不能宣称 PR 更新瞬间就撤回正在进行的调用。

发布前继续执行现有仓库、PR、head、可信产物和机器人评论校验。远端查询失败时禁止发布无法确认版本的报告。

## 10. 运行状态、运行事件与 trace 的边界

运行状态表示当前进度；checkpoint 和单元结果供自动恢复使用。运行事件保存发生过的状态变化，供人工查看、命令行展示和后续通知。trace 保存调用细节，供诊断性能和错误。

| 数据 | 必须保存的内容 | 自动计算/人工用途 |
|---|---|---|
| 任务/单元状态 | 当前状态、固定输入、取消、预算、已完成输出 | 恢复、是否调用模型、能否发布的判断依据 |
| 运行事件 | 入队、领取、排队超时、开始、单元完成、尝试失败、安排重试、恢复、预算耗尽、取消、取代、任务结束 | 按序展示、审计；不依赖重放全部事件才能恢复任务 |
| trace | 模型/工具调用耗时、用量、异常堆栈、关联编号 | 排查问题；第一版不参与审查判定、恢复或预算计算 |

事件至少包含 `event_id`、`run_id`、`execution_id`、可选 `unit_id/attempt_id`、类型、时间、任务内单调序号、脱敏载荷和可选 trace 关联 ID。事件按任务序号展示，不能只按时间戳排序。消费端以 `event_id` 去重。

入队尚无执行进程时 `execution_id` 可为空，领取后关联本次执行编号。并发单元的事件序号由持久层原子分配，不能通过各协程各自计算最大序号加一产生冲突。

状态变化与对应 SQLite 事件在同一事务保存。事件导出到 JSONL/控制台失败不回滚业务状态；数据库内事件保存失败则该次事务失败。无需实现通用事件溯源框架。

Trace 第一版可用结构化本地日志，不强制购买观测服务。trace 写入失败不得令已成功的审查失败；输出降级提示即可。默认不在事件和 trace 保存完整代码、完整提示词、模型响应或 Secret。为恢复保存的必要模型结果属于受访问控制的业务状态，不等同于 trace。

状态分两层，避免把“进程停了”误认为“代码没问题”：

- runtime 生命周期：`queued/running/interrupted/completed/cancelled/superseded/failed`。其中 `completed` 表示运行结束，不代表完整覆盖代码。
- 审查结果：沿用 `completed/skipped/incomplete/failed/superseded`。取消时保留已完成结果，记录取消原因，不宣称覆盖完整；可输出 `incomplete` 并附 `runtime_status=cancelled`。

CLI 需区分正常完成、部分完成、失败和人工取消。保留已有审查退出码语义；人工取消建议 130，`superseded` 沿用 0。新生命周期和旧报告 schema 的映射必须文档化并有验证。

## 11. SQLite 最小数据设计

表名可调整，以下数据职责必须具备：

| 数据 | 关键约束 |
|---|---|
| `runs` | `run_id` 唯一；固定输入、状态、取消、提交时间、首次执行时间、排队时限、执行截止时间、schema 版本 |
| 调度所有权 | 任务的执行者标识、执行槽与进程身份；领取原子化，结合进程锁核对存活情况 |
| `units` | `(run_id, unit_id)` 唯一；输入摘要、输出、执行状态 |
| `attempts` | `attempt_id` 唯一；单元、次数、预占、错误类别、开始/结束/下次重试时间 |
| 预算台账 | 请求预占、已知/未知用量、上下文计量，恢复不清零 |
| `events` | `event_id` 唯一；任务内序号唯一；与状态变化原子保存 |
| 发布记录 | 目标 PR、head、报告摘要、远端评论 ID、成功/失败/结果未知 |
| LangGraph checkpoints | 采用与项目版本兼容的官方 saver，明确与业务表的恢复协调 |

提供 schema 版本和可重复执行的初始化。遇到新于程序支持范围的 schema 必须拒绝运行，不能删除数据库重新初始化。第一版提供显式清理命令或步骤，默认不自动删除未完成任务。

## 12. 操作入口与交付

提供以下能力，命令拼写可按现有 CLI 统一：

```text
runtime start    创建固定输入任务并持久化入队，立即返回 run_id
runtime serve    启动唯一管理进程，管理最多两个执行进程
runtime resume   将符合恢复条件的中断任务按原 run_id 重新入队
runtime status   查询排队/执行状态、已完成文件、预算和阻塞原因
runtime events   按序查看或导出运行事件
runtime cancel   写入取消请求
```

受理成功输出 `run_id`、数据库路径、查询命令；管理进程未运行时明确提示任务仅已保存、尚未执行。`status` 不需要模型 Key，并展示等待任务数、两个执行槽占用和任务内模型在途数。恢复失败应说明是预算、版本、PR 更新、缺少 Git 对象还是执行所有权问题。

所有正式执行入口，包括手动恢复，必须经过同一服务级并发控制；不能另留一个不限并发的直接执行入口。可保留仅供调试的无服务模式，但必须显式声明隔离数据库和不与正式服务混跑。

交付代码、数据库初始化/版本管理、配置示例、故障演示脚本、操作手册、测试结果和已知限制。文档注明数据目录、访问权限、备份/恢复、未知模型用量和旧任务处理方式。

另外交付第 3.3 节的同步阻塞检查与改造对照表，以及事件循环延迟、正向并发和负向阻塞对照的实测记录。静态检索只能定位候选调用，不能替代运行验证。

自动化演示使用 fake LLM 与 fake GitHub，不消耗真实模型额度，不发布真实评论。需要真实端到端联调时另行记录凭据条件和运行链接，不能用模拟结果冒充真实验收。

## 13. 验收场景

| 场景 | 必须观察到的结果 |
|---|---|
| 10 文件，4 个结果保存后强制结束进程 | 新进程读取相同 DB，这 4 个不调用模型，其他按保存状态继续；使用真实跨进程验证，不依赖完成顺序 |
| 模型响应已保存、核验前崩溃 | 恢复复用已保存响应，不再次请求模型 |
| 文件结果保存后、图 checkpoint 保存前崩溃 | 节点重放复用唯一结果，不重复调用或汇总 |
| 同一单元多次请求保存 | 数据库只有一份生效结果，报告没有重复发现 |
| 429 后成功 | 有退避和重试事件；所有实际调用计入预算 |
| 无效 JSON 重试耗尽 | 明确未完成，结果不是零问题的 `completed` |
| 无效 Key/输入解析错误 | 不盲目重试，指出错误类别与阶段 |
| 剩余 1 次请求，失败后恢复 | 不能因恢复再得到请求额度 |
| 请求预占后强制退出 | 尝试与预占可见，额度不返还；不确定用量明确展示 |
| 恢复时已超过原截止时间 | 不发新请求，保留已有结果并说明超时 |
| 重试等待时人工取消 | 最迟在下一次取消检查时退出等待，不继续请求 |
| 正在调用模型时取消 | 返回/超时后停止后续工作，不发布；不声称撤回供应商计费 |
| PR 更新或恢复时 head 不一致 | 旧任务 `superseded`，不发布旧 head 报告 |
| 同时提交三个独立 PR | 最多两个任务执行，第三个持久化排队，空出执行槽后开始 |
| 两个 worker 竞争同一待执行任务 | 仅一个原子领取成功，另一个领取其他任务或等待 |
| 重复启动管理进程 | 第二个报忙，不产生额外执行槽；原管理进程退出后正确处理存活子进程 |
| 每个任务至少有六个独立文件等待模型 | 单任务在途请求峰值不超过 5，两个任务合计不超过 10；用 fake LLM 屏障实测 |
| 剩余一次累计请求预算时多个协程竞争 | 只允许一次预占和发送，不因并发而超出预算 |
| 模型名额用尽，第六个请求等待 | 其他请求能返回、取消检查能运行；释放一个名额后第六个才能发送 |
| 一个外部调用长时间等待 | 同进程其他协程、进度与取消响应不被同步调用堵住 |
| 第 3.3 节模型、GitHub、Git 和退避路径逐项运行 | 可控慢响应期间其他协程继续推进；按受控心跳阈值验证，覆盖间接调用而非只检查外层函数声明 |
| 人为引入同步阻塞的负向对照 | 心跳检测能够识别停顿；不能使用完全不经过实际适配层的 fake 蒙混通过 |
| 同步调用经线程池运行后上层取消 | 底层未结束期间不提前归还本地请求名额或错误释放执行槽 |
| SQLite 写锁等待、checkpoint 或同步文件操作较慢 | 不长时间堵住事件循环；跨线程连接使用符合驱动约束，取消和名额限制仍生效 |
| 接收成功后、worker 领取前进程重启 | SQLite 中任务仍可查询，并被服务继续领取 |
| 第三个任务排队后才首次开始 | 审查执行时间从首次领取计算；初次排队时间不消耗执行预算 |
| 排队容量已满或等待超时 | 明确拒绝或标记 `queue_timeout`；不静默丢失已受理任务 |
| 排队中取消或同 PR 新 head 入队 | 旧待执行任务不调用模型，新任务不与同 PR 旧执行者同时运行 |
| GitHub 创建成功但本地未保存成功 | 再次执行先查询并复用已有评论；不能重复创建 |
| GitHub 查询失败且上次创建结果未知 | 保留未知状态，不盲目创建第二条 |
| SQLite 写锁或写入失败 | 不把持久化失败当成功，不因保存重试再次调用模型 |
| trace 输出失败 | 核心审查照常，状态与预算正确；无 Secret 泄漏 |
| 输入配置或 schema 不兼容 | 明确拒绝恢复，不悄悄变更审查依据 |
| 一致性备份恢复 | 新路径启动可查询任务并恢复符合条件的未完成工作 |

同时保持现有 diff 范围、规则引用、证据核验、超预算 `incomplete`、发布校验和旧入口的回归检查。不得放宽验证门槛来通过测试。

## 14. 实施顺序

1. 明确单元身份、状态转换和 SQLite 数据结构，完成跨进程状态保存和任务持久化入队。
2. 将逐文件审查接入可恢复单元，处理模型响应保存和图 checkpoint 重放。
3. 持久化预算，统一异常与重试策略，消除多层重试。
4. 实现唯一管理进程、两个执行槽、原子领取与进程退出恢复。
5. 逐项处理第 3.3 节已知同步阻塞路径，接入任务内共享五个模型名额的异步执行，验证事件循环延迟、并发预算和结果隔离。
6. 接入取消、PR 更新检查、发布重复执行处理。
7. 统一运行事件和 trace 关联，完成故障注入验收与使用文档。

开发 Agent 先检查实际发布仓库的版本和已有实现；发现与本文假设冲突时记录具体差异。不得顺手修改规则内容、开启修复循环、创建远端仓库或部署服务。
